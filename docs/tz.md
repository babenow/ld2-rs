## 1. Назначение и общая картина

### 1.1 Что это

**«ld2»** — текстовая онлайн-MMORPG: мир представлен текстовыми локациями с переходами
(«на север», «по дороге на запад» и т.п.), весь игровой процесс отражается в текстовых панелях
и логах. Клиент — нативное desktop-приложение на Rust (egui/eframe) для Windows, macOS и Linux.

### 1.2 Core gameplay loop

```
выбор персонажа → вход в локацию → бой с монстрами / квесты → опыт в навыки, лут
→ экипировка / улучшение предметов / магия → смерть = потеря всего лута → возврат в город
социальный слой: чат, группа, торговля, гильдии, преступления и статусы
```

### 1.3 Ключевые сущности мира (для UI и контракта)

| Сущность | Описание |
|---|---|
| Аккаунт | Логин в игру. На аккаунте 1…N персонажей, `N` задаёт сервер (динамический лимит). |
| Персонаж | Атрибуты, навыки (прокачка очками опыта), инвентарь, экипировка, профессии, квесты, статусы. |
| Локация | Текстовое описание, список NPC/монстров/игроков, выходы (`exit_id` → текстовое название направления), правила (безопасная зона / PvP-зона). |
| Предмет | Свойства, слот экипировки, уровень улучшения (+1…+N), сокеты (для посохов), руны, свитки. |
| Квест | Цели, награды (XP/предметы), статус: доступен/взятов/выполним/сдан. |
| Статус преступления | Вид («Убийца», «Мародёр», …) + истечение по времени. |

### 1.4 Глоссарий

- **Лут** — предметы, выпавшие с мобов/на трупах. При смерти персонажа **весь лут (инвентарь+экипировка) теряется**.
- **Мародёрство** — сбор лута с трупа другого *игрока*; вешает статус «Мародёр».
- **Частичное сложение** — правила накопления времени статуса: см. §4.10.
- **Свиток** — одноразовое заклинание, применяется из инвентаря.
- **Руна** — предмет-заклинание с зарядами; инкрустируется в сокет посоха, кастуется из него.
- **Сокет** — слот для руны на предмете (обычно посох). Число сокетов зависит от предмета и улучшения.
- **Hotbar** — панель привязанных действий (скиллы/руны/предметы) на клавиши.

## 2. Границы и допущения

### 2.1 Границы этого ТЗ

**В объёме:**
- desktop-клиент (основной продукт документа);
- контракт протокола клиент↔сервер (JSON поверх WebSocket) — полная спецификация §4;
- **мок-сервер** на Rust, реализующий контракт со скриптованными сценариями (§5) — необходим,
  поскольку реального сервера нет; он же используется в интеграционных тестах клиента;
- CI/CD, кросс-платформенная сборка, автоматическое обновление.

**Вне объёма:**
- реальный игровой сервер, его БД и балансировка (контракт §4 — основа для будущего отдельного ТЗ на сервер);
- баланс (числа XP, стоимости, шансы улучшения) — задаётся константами мока и помечен как настраиваемый;
- мобильные версии, веб-версия.

### 2.2 Допущения (утвердить при приёмке §14)

| # | Допущение |
|---|---|
| A1 | Мир обновляется **в реальном времени push-событиями** сервера (бой, чат, изменения локации, таймеры статусов). Единственный источник истины — сервер; клиент ничего не считает сам, кроме локального обратного отсчёта таймеров. |
| A2 | Состояние клиента собирается из **полного снапшота** при входе/переподключении и **инкрементальных событий** далее (§4.2). |
| A3 | Бой real-time, но дискретный: сервер шлёт события ударов/раундов; клиент не требует покадровой анимации — текстовый бойлог + полоски HP достаточны. |
| A4 | Авторизация по логину/паролю; сервер выдаёт короткоживущий access-token и refresh. Пароли клиента нигде не хранятся в открытом виде; токены — в ОС-хранилище (keychain/credential manager). |
| A5 | Один клиент = одна сессия аккаунта; «многокорповость» (несколько окон/аккаунтов) — не в v1, но архитектура не должна её исключать (одна копия приложения на аккаунт/профиль конфигурации). |
| A6 | Голос, стриминг, RMT — вне игры. |

## 3. Функциональные требования (ФР)

Обозначения: **УИ** — элементы интерфейса, **Д** — данные, **П** — поведение/краевые случаи.
Каждое требование имеет ID (ФР-xx) для трассировки в тестах и коммитах.

### ФР-01. Авторизация и аккаунт
- УИ: экран входа (login, password, «Запомнить аккаунт»), индикатор соединения, кнопка «Переподключить».
- П: повторный вход по сохранённому токену без ввода пароля; при 401/истечении refresh — возврат на экран входа
  с сохранением черновиков UI-настроек; разрыв соединения не должен терять аккаунт (см. ФР-02, reconnect).
- П: при первом успешном входе клиент показывает **конфиг аккаунта**, присланный сервером
  (лимит слотов персонажей, включённые фичи) — см. `evt/session.start` §4.8.1.

### ФР-02. Персонажи аккаунта
- УИ: экран выбора персонажа: список карточек (имя, класс/профессии, уровень-сводка, локация, статусы), кнопка «Создать», «Удалить» (с подтверждением).
- Д: `char_slot_limit` приходит от сервера и **не захардкожен в клиенте** — при увеличении лимита сервером клиент обязан показать дополнительные слоты без обновления клиента.
- УИ: создание — мастер: имя (проверка уникальности сервером, live-валидация) + выбор **стартового профиля** (Воин/Вор/Маг — наборы стартовых навыков; без рас и классов в v1). Список профилей и их состав присылает сервер (`cmd/char.create { name, profile }`, capability-driven).
- П: мгновенное переключение между персонажами аккаунта без ре-логина (`cmd/char/select` → полный снапшот);
  текущий персонаж выгружается корректно (сброс сторов, отписки от каналов).

### ФР-03. Мир: локация и навигация
- УИ: центральная панель «Локация» (см. §7.1):
  - заголовок: имя локации + теги правил (`PvP`, `безопасная`, `подземелье`);
  - текст описания (прокручивается);
  - панель **выходов**: кнопки по каждой ссылке (`→ север`, `→ дорога на запад`, …) с горячими клавишами Alt+стрелки;
  - списки: игроки в локации, NPC, монстры, трупы (каждая строка: имя, полоска HP, теги-статусы).
- УИ: контекстное меню на сущности: *атаковать / заговорить (whisper) / предложить сделку / пригласить в группу / осмотреть труп* — набор действий зависит от роли сущности и правил локации (в безопасной зоне «атаковать» скрыто).
- Д: карта/граф локаций: клиент хранит посещённые локации (кэш `location_id → имя/выходы`); визуальная граф-карта — **не в v1**, в v1 список посещённых локаций с быстрым повторным переходом из истории.
- П: попытка хода в несуществующий/заблокированный выход обрабатывается ошибкой сервера с понятным тостом; телепорт/смерть меняют локацию — снапшот приходит автоматически.

### ФР-04. Навыки и опыт
- Д: персонаж имеет атрибуты (например Сила/Ловкость/Выносливость/Интеллект/Дух — **состав определяет сервер**, клиент рендерит произвольный набор) и навыки, получающие очки опыта; прогресс навыка = накопленный XP (пороги считает сервер). **Полная модель опыта и список навыков — [`skills.md`](./skills.md).**
- УИ: лист персонажа (вкладка «Навыки»): группы навыков, текущее значение, XP до следующего ранга (прогресс-бар), сортировка; вкладка «Атрибуты».
- П: каждое событие `evt/char/xp` (убийство моба, сдача квеста) отображается всплывающей строкой в боевом/системном логе («+142 XP в «Владение мечом» (61%)») и обновляет лист; лента начислений — в журнале (последние N записей, настраиваемо).
- П: повышение ранга навыка — отдельное событие с маркированным тостом.

### ФР-05. Бой
- УИ: панель «Бой»: текущая цель (имя, HP-бар, статы), **HP/mp-бары своего персонажа** (mp — ресурс заклинаний, см. ФР-09 и `skills.md` §2.4), лог ударов с цветовой кодировкой (входящий/исходящий/крит/промах/магия), hotbar действий (атака, скиллы, руны, зелья), кнопки «Отступить/сбежать» если сервер это поддерживает.
- П: цель выбирается кликом по сущности в локации или клавишей Tab (цикл по врагам); авто-сброс цели при гибели/исчезновении.
- П: бои других игроков в локации отображаются в лог локации (что видно всем) — без детализации чужих статов, только то, что транслирует сервер.
- П: команда «атаковать» мгновенно (отклик ≤ 500 мс на нормальной сети); спам команд защищается сервером, клиент показывает cooldown, если сервер прислал (`evt/combat/cooldown`).

### ФР-06. Смерть и потеря лута
- Д: при смерти персонажа **все предметы инвентаря и экипировки теряются** (становятся лутом/трупом по правилам сервера).
- УИ: модальное окно «Вы погибли» со сводкой утраченного (список из payload `evt/char/death`, см. §4.8.7), подтверждение → respawn (город/последний костёр — как скажет сервер), затем полный снапшот пустого инвентаря.
- П: окно нельзя закрыть молча — только подтверждением (потеря необратима, UX должен это утрировать);
  если сервер прислает «страховочный набор» (стартовый лут после смерти) — он появится обычным `evt/item/added`.

### ФР-07. Инвентарь и экипировка
- УИ: сетка инвентаря (фикс. ёмкость от сервера), drag&drop в слоты экипировки и обратно, контекстное меню предмета: *использовать, надеть, снять, улучшить, вставить руну (если посох), выбросить, показать описание*.
- Д: предмет отображает: имя, тип/подтип, rarity-цвет, статы, **уровень улучшения (+N)**, сокеты (`◈◈○` — занято/свободно), требования (атрибуты/профессия/уровень), вес, ценность.
- П: предметы, не подходящие по требованиям, надеть нельзя — сервер отклоняет, клиент показывает причину из ошибки; tooltip недоступного требования подсвечивается красным.
- П: лут из монстра — тост + автодобавление в инвентарь (или окно «выбор лута», если сервер присылает `roll`-механику — режим capability-driven).

### ФР-08. Профессии
- Д: набор профессий определяет сервер (например: алхимик, кузнец, начертатель, травник — пример, не догма). Персонаж может изучать профессии (условия/лимиты — сервер). **Список профессий, цепочки сырья и структура рецептов — [`skills.md`](./skills.md).**
- УИ: вкладка «Профессии»: изученные профессии с уровнями и XP, список рецептов (ограниченных профессией) с требованиями (ингредиенты, инструменты, локации-станки); крафт как последовательность `cmd/craft.start` → `evt/craft/result`.
- П: рецепты без ингредиентов отображаются с красной подсветкой нехватки (клиент сверяет с локальным инвентарём, итог решает сервер).
- П: улучшение предметов (§4.9/ФР-10) может требовать профессию/станок — правила сервера, клиент показывает `requires` из данных рецепта/услуги.

### ФР-09. Магия: свитки и руны
- Д:
  - **Мана (mp)** — общий ресурс заклинаний: максимум растёт с `int` и рангом `arcana` (формула — `skills.md` §2.4), реген — по правилам сервера (вне боя быстро, в бою медленно). Каст руны тратит **ману и заряд** руны; свиток ману **не тратит** (сам свиток и есть расходник).
  - **Свиток** — одноразовый предмет; применение: выбрать цель (или авто-на себя) → `cmd/item.use`.
  - **Руна** — предмет с N зарядами и заклинанием; инкрустируется в свободный сокет **посоха**; кастуется с посохом в экипировке; заряды тратятся при касте, восстанавливаются маслом алхимика (предмет, по правилам сервера).
  - **Посох** — экипируемый предмет с сокетами; количество сокетов зависит от базы и уровня улучшения (данные сервера).
- УИ: «Инкрустация» — окно предмета-посоха: схема сокетов (кликабельные слоты ◈), список доступных рун из инвентаря; извлечение руны; подтверждение стоимости операции, если сервер её указывает.
- УИ: каст с руны — в hotbar можно привязать «посох.сокет_2»; активная иконка показывает остаток зарядов (бейдж «×7») и стоимость в мане в tooltip.
- П: каст без заряда / без посоха в руках / **без маны** — блокировка на клиенте (иконка приглушена + tooltip причины: `E_NO_CHARGES`, `E_NOT_ENOUGH_MP`) и, при гонке состояний, корректная обработка ошибки сервера.
- П: событие каста (`evt/magic/cast`, поля `charges_left` и `mp_left`) с текстом «Вы произнесли «Огненная стрела» (руна, зарядов: 6, маны: 45)» попадает в бойлог; чужие касты в локации — в лог локации.

### ФР-10. Улучшение предметов
- Д: предмет имеет уровень улучшения `+0…+max`, растущий по `evt/upgrade/result` (успешно — +1; провал — по правилу сервера: без потери уровня / уровень падает / предмет разрушается; набор правил capability-driven в `evt/session.start.upgrade_rules`).
- УИ: диалог «Улучшение»: превью предмета «сейчас → после» (дельта статов от сервера, `preview_id` из `cmd/upgrade.preview`), стоимость (деньги/материалы), шанс успеха (если сервер его раскрывает), кнопка «Улучшить», результат — тост + подсветка слота.
- П: процесс может быть длительным (очередь/таймер сервера) — клиент показывает прогресс-статус и позволяет закрыть диалог; завершение придёт событием в любой момент; итоговый `+N` отражается везде, где предмет отображается.

### ФР-11. Преступность и статусы
- Д:
  - виды статусов (пример, расширимо сервером): **Убийца** (убийство игрока), **Мародёр** (лут с трупа игрока), **Вор** (карманная кража у игрока; включается серверным конфигом `crime.kinds`, в моке — активен), + любые новые `kind` из контракта (клиент не должен падать на неизвестном kind — generic-рендер по payload);
  - каждый статус имеет `expires_at` (абсолютное время, серверная истина) и уровень опасности (severity: low/medium/high — цвет бейджа);
  - **частичное сложение**: при новом преступлении время статусов складывается нелинейно (формула на сервере, §4.10; клиент **не пересчитывает** — только отображает результат: новые `statuses[]` из `evt/crime/status`).
- УИ:
  - бейджи статусов у имени персонажа (везде, где отображается имя: свой хедер, список локации, чат-префикс) + обратный отсчёт «Убийца · 6ч12м» (обновление раз в 1 с, округление вверх до минут для чужих);
  - вкладка «Статусы» в листе персонажа: активные + журнал нарушений (последние N, из `evt/crime/log`) с текстом «За мародёрство: +3ч 20м»;
  - цвет/иконка по severity; при входе в PvP-зону с активным статусом — предупреждающий тост (правила зоны от сервера).
- П: истечение статуса — событие `evt/crime/removed` **и** локальный fallback-пересчёт по `expires_at` (защита от потерь событий); после истечения бейдж исчезает, журнал остаётся.
- П: UI жертвы: если убили вас/игрока — текст локации/бойлог различает «монстр» и «игрок» (данные сервера), что важно для понимания, почему можно стать мародёром: **сбор с трупа игрока** клиент помечает предупреждением перед подтверждением («труп игрока — вы получите статус «Мародёр» на ~Xч» (X из данных сервера, если есть; иначе без числа)).

### ФР-12. Квесты
- УИ: журнал квестов: активные (цели с прогрессом «2/5»), доступные (от NPC/локации), выполненные (сдать). Трекер: 1–3 выбранных квеста — компактно в правой колонке.
- П: вздача — диалог с наградой (XP/предметы), до подтверждения награда не начисляется (данные сервера); авто-обновление прогресса по событиям убийств/сбора (`evt/quest/progress`).
- П: недоступный квест (нет NPC/региона) — в списке с пометкой; сортировка/фильтр по локации выдачи.

### ФР-13. Чат
- УИ: нижняя панель с вкладками/каналами: **системный, локация, глобальный (мир), группа, гильдия, шёпот** (whisper); фильтр-строка; настройка «скрывать боевой лог из чата/смешивать» (локально).
- Д: сообщение = канал, автор (с бейджами статуса), текст (разметка: ссылки на игроков/предметы, если сервер присылает structured payload — рендер по capability, plain text обязателен как fallback).
- П: история хранится кольцевым буфером (по умолчанию 5 000 сообщений/канал, настраиваемо, NFR §8); переключение персонажа **сбрасывает** историю (это разные сущности); whisper-сессии (последний адресат, кнопка «ответить»).
- П: отправка команд с префиксом `/` (`/w Имя текст`, `/p текст`, `/join гильдия`…) — клиент парсит, превращает в `cmd/chat.send`; неизвестная команда — ошибка тостом, не отправляется в чат как текст.

### ФР-14. Группа (пати)
- УИ: виджет группы (сворачиваемый) вверху слева: участники (имя, HP/мана бары, локация, ready-статус), лидер; панель приглашений/ролей.
- П: создание/приглашение/принять/отклонить/исключить/покинуть — `cmd/party/*`; приглашение — модальное окно с таймаутом, если сервер его задал.
- П: распределение лута в группе — режим диктует сервер (`roll`/`free-for-all`/`leader`): клиент показывает то, что есть в `evt/corpse/lootable` (капability).

### ФР-15. Торговля между игроками
- УИ: окно сделки из двух колонок (я/партнёр): слоты предметов, поле золота, «Предложить», «Принять», «Отмена»; блокировка взаимного одобрения (галочка «принято» становится неактивной при изменении состава — сброс сервером `trade_version`).
- П: сделка открывается только в одной локации с партнёром (проверка сервером; клиент подсказывает); любые расхождения состояний — по `trade_version` (старая версия отклоняется).
- П: анти-абуз: клиент показывает итоговую оценку стоимости сделки по данным сервера (если передано `value_hint`), предупреждение о безвозвратности.

### ФР-16. Гильдии/кланы
- УИ: вкладка «Гильдия»: информация (имя, герб-эмодзи/цвет, состав с рангами и статусом online/локацией), мой ранг; список гильдий (поиск/сортировка), заявки (для мастера), приглашения.
- П: операции: создать (по правилу сервера — стоимость/уровень), вступить/выйти/исключить, смена ранга/прав (для мастера), титул, гильдейский банк **не в v1** (место в контракте зарезервировано `guild.bank.*` — не реализовывать).
- П: гильдейский чат = канал ФР-13; события вступления/выхода/изменения ранга — в системный лог.

### ФР-17. Журналы
- УИ: единый прокручиваемый «Лог мира» (лог текущей локации + системные), опционально боевой лог отдельным фильтром. Экспорт в файл (txt) — v1.1-фича, не блокирующая.
- П: типы строк визуально различимы: окружение (серый), лут (золотой), бой (красный/зелёный), магия (синий), преступление/статусы (оранжевый/красный), квест (фиолетовый) — см. палитру §7.4.

### ФР-18. Уведомления
- П: событийные тосты в приложении (egui-toast): получение предмета, уровень навыка, приглашение в группу/сделку, изменение статуса преступления, результат улучшения, смерть.
- П: фоновые OS-уведомления (notify-rust / Windows / NSUserNotification) — **опционально, за feature-flag** (`desktop.notify`), с настраиваемым списком событий. **По умолчанию включены 4 события (решение D7):** смерть персонажа · приглашение в пати/сделку · личные сообщения (whisper) · результат улучшения предмета.

### ФР-19. Настройки и состояние UI
- УИ: окно настроек: тема, размер шрифта, горячие клавиши (ремаппинг всех действий), лимиты истории, поведение окон, язык (ru/en), хост сервера (для dev/тестов: `ws://` только с предупреждением и запретом в release-сборке по умолчанию).
- П: состояние окон/панелей (размеры, раскрытые вкладки, размер шрифта) сохраняется между запусками; импорт/экспорт конфига.

## 4. Контракт сетевого протокола

Сервера нет — этот раздел является нормативным контрактом для (а) клиента, (б) мока (§5), (в) будущего реального сервера.
**Полный развёрнутый контракт живёт в [`protocol.md`](./protocol.md)** (этот раздел — краткое изложение; при расхождениях истина — `protocol.md` + `ld2-protocol` crate).

### 4.1 Транспорт

- **WebSocket поверх TLS** (`wss://`); dev-режим допускает `ws://` против localhost/мока.
- Одно текстовое JSON-сообщение за кадр (`DataFrame`). Макс. размер сообщения — 64 KiB (иначе `E_TOO_LARGE`); крупные данные (снапшоты) сервер нарезает на несколько событий.
- Ping/Pong на уровне WS для keepalive; на уровне прикладного протокола — `cmd/ping → evt/pong` (замер RTT).

### 4.2 Модель состояний: снапшот + delta + события

- Сервер — единственный источник истины. Каждое состояние имеет монотонный `state_version` (u64 на сессию персонажа).
- При `cmd/char/select` и при переподключении сервер шлёт `evt/state/snapshot` (полное состояние персонажа+локации+видимого).
- Далее — только `evt/…` события. Если клиент пропустил события (разрыв), он шлёт `cmd/state/resync { last_state_version }`: сервер отвечает либо `evt/state/delta` (если может), либо новым полным снапшотом.
- Клиент обязан корректно пережить получение снапшота в любой момент (полная замена сторов).

### 4.3 Конверт сообщения

```json
// → сервер (команда)
{ "v": 1, "type": "cmd/location.move", "seq": 42,
  "ts": "2026-11-02T21:05:11Z", "payload": { "exit_id": "e_north" } }

// ← сервер (подтверждение команды)
{ "v": 1, "type": "ack", "seq": 42, "state_version": 1337,
  "result": "ok" }

// ← сервер (ошибка команды)
{ "v": 1, "type": "ack", "seq": 42, "result": "error", "state_version": 1337,
  "error": { "code": "E_EXIT_BLOCKED", "message": "Выход завален — сначала разберите завал" } }

// ← сервер (событие)
{ "v": 1, "type": "evt/chat.message", "ts": "2026-11-02T21:05:12Z",
  "payload": { "channel": "location", "from": "player_77", "text": "who wants party?" } }
```

Правила:
- `v` — версия протокола (int). Неизвестный `type`/`v` → клиент логирует, игнорирует, не падает.
- `seq` (u32, оборачивается) присваивает клиент; на каждую команду ровно один `ack` (или таймаут клиента = 10 с, `E_TIMEOUT` локально).
- Идемпотентность: повтор команды с тем же `seq` в рамках сессии не должен давать двойного эффекта (сервер хранит окно последних 128 seq).
- `ts` — ISO-8601 UTC. Клиент калибрует смещение серверного времени (см. §4.4) и **все absolute-дедлайны хранит в серверных epoch-секундах**.
- Именование: `cmd/<domain>.<action>`, `evt/<domain>.<event>` — домены: `session, auth, char, location, entity, combat, item, magic, socket, upgrade, craft, quest, crime, chat, party, trade, guild, state, time`.

### 4.4 Время, задержки

- `cmd/time.sync` → `evt/time.sync { server_ts, rtt_hint }` — клиент оценивает `server_time_offset` (медиана из 5 замеров при старте и периодическая перекалибровка раз в 5 мин).
- Все локальные обратные отсчёты (статусы, cooldown'ы, таймеры сделки) = `expires_at (epoch, сервер) − now_adjusted`.

### 4.5 Сессия и авторизация

```
connect → cmd/auth.register { login, password } → ack + evt/session.start (регистрация = вход; лимиты — настройки сервера)
или     → cmd/auth.login { login, password } → ack + evt/session.start (config аккаунта, токены)
reconnect → cmd/auth.resume { refresh_token } → evt/session.start | E_AUTH_EXPIRED
cmd/session.refresh — продление access-token (клиент трекит expiry − 60 с).
```

- Потоки токенов: `access_token` (15 мин) для WS-сессий, `refresh_token` (30 дней) хранится в keyring.
- `cmd/auth.logout` — отзыв refresh.

### 4.6 Конфиг аккаунта и capabilities

`evt/session.start.payload`:

```json
{
  "char_slot_limit": 8,
  "protocol_features": {
    "trade.value_hint": true, "loot.roll": false, "respawn.inn": true,
    "guild.bank": false, "upgrade.rules": "break_on_fail"
  },
  "crime": { "t_max_s": 604800, "base": { "murderer_s": 21600, "marauder_s": 7200 },
              "blend_k": 0.5 },
  "chat": { "server_history": 200, "channels": ["system","location","global","party","guild","whisper"] },
  "upgrade": { "max_level": 9, "preview": true }
}
```

Клиент обязан: а) не требовать наличия неизвестных ключей; б) менять поведение по `protocol_features` (graceful capability flags); в) все лимиты брать из конфига, не из констант.

**4.8.1 `evt/session.start`** — §4.6 + `characters[]` (сводки).

**4.8.2 `evt/state/snapshot`**

```json
{
  "state_version": 1337,
  "char": { "id": "c1", "name": "Ким", "attrs": {"str": 14, "int": 9},
            "skills": [{"id":"sword","rank":3,"xp":612,"xp_to_next":480}],
            "professions": [{"id":"scribe","rank":2,"xp":140}],
```

**4.8.3 `evt/char/xp`** `{ skill_id, amount, skill_xp, rank?, xp_to_next }` (rank присутствует при повышении).
**4.8.4 `evt/location/changed`** — новый блок `location` (полностью, компактный).
**4.8.5 `evt/entity/spawn|move|despawn|hp`** — точечные апдейты списков.
**4.8.6 `evt/combat/hit`** `{ source, target, kind:"melee|rune|scroll|skill", amount, crit, miss, text }` — `text` серверный (клиент рендерит как есть, локализацию боёвки не дублирует).
**4.8.7 `evt/char/death`** `{ victim_char:true, lost_items:[{uid,name,rarity}], corpse:"cor_10", respawn:{location_id, delay_s} }`.
**4.8.8 `evt/crime/status`** `{ statuses:[…], log_hint:"За мародёрство: +3ч 20м" }` — полная замена списка; журнал — по запросу `cmd/crime.log`.
**4.8.9 `evt/item/state`** `{ uid, patch }` — патч предмета (например `{"upgrade":3,"sockets":[…]}`) для улучшений/инкрустаций.
**4.8.10 `evt/upgrade/result`** `{ uid, ok, new_upgrade?, item_destroyed?, cost:{gold,materials} }`.
**4.8.11 `evt/magic/cast`** `{ by, what, target?, charges_left?, mp_left?, ok }`.
**4.8.12 `evt/trade/state`** `{ offer_id, version, you:[…], them:[…], you_locked, them_locked }` — каждое изменение = новый `version`.
**4.8.13 `evt/chat/message`** — §4.3 пример.
**4.8.14 `evt/state/delta`** `{ from_version, to_version, patch: [ {path, op, value} ] }` — RFC-6902-like (реализация — свой простой subset, не обязательная RFC-полнота).

### 4.9 Коды ошибок (в `ack.error.code`)

Транспортно-agnostic UPPER_SNAKE: `E_AUTH_EXPIRED, E_NOT_IN_LOCATION, E_EXIT_BLOCKED, E_TARGET_GONE,
E_NO_CHARGES, E_REQUIREMENT_ATTR, E_PROFESSION, E_INVENTORY_FULL, E_TRADE_STALE, E_GUILD_LIMIT,
E_RATE_LIMITED, E_TOO_LARGE, E_INTERNAL`. Клиент мапит код → человекочитаемое сообщение локализации; `message` сервера — резервный текст.

### 4.10 Преступность: серверная модель «частичного сложения» (предлагаемая)

Обозначим текущий срок наказания `T` (секунды), срок нового преступления `t`, потолок `T_MAX` (из конфига, пример: 7 суток).

```
T_new = min(T_MAX, T + k · t · (1 − T / T_MAX)),  k = blend_k (пример: 0.5..1)
```

Смысл: за overlapping-преступления сроки складываются с убывающим вкладом (каждое новое добавляет меньше, при `T → T_MAX` добавка → 0). Статусы разных `kind` сосуществуют отдельно (каждый со своим `expires_at`); формула описывает эскалацию общего срока «преступник». Мока достаточно этой модели; реальный сервер вправе заменить формулу — **клиент не пересчитывает**, только рендерит `statuses[]` и `log_hint`.

Примеры (k=0.5, T_MAX=604800): первый «Убийца» 21600 → 21600; затем «Мародёр» 7200 → 21600 + 0.5·7200·(1−21600/604800) ≈ 24741 с (≈6ч52м); и т.д.

### 4.11 Версионирование

- `v` в конверте; несовместимые изменения = новый `v` + отдельная ветка контракта;
- идемпотентность типов: новый optional-пол — совместимо; удаление/переименование — несовместимо (bump `v`);
- клиент при неизвестном `v > 1` — предупреждение «Требуется обновление клиента» + вход блокируется (кроме режима dev).

## 5. Мок-сервер

Цель: полностью детерминированный стенд для разработки/тестов клиента без реального бэкенда.

- Реализация: отдельный bin в workspace (`crates/ld2-mock-server`), `tokio` + `tokio-tungstenite`, тот же crate `ld2-protocol`.
- Функциональность:
  - авторизация по фиксированным тестовым аккаунтам (например `demo/demo123`);
  - скриптованные сценарии: «деревня → лес → бой с волками → лут → смерть → труп игрока → мародёрство → статусы», «сделка», «пати», «каст с руны», «улучшение +0→+3 с провалом»;
  - генератор случайных событий (чужие сообщения в чате, хп-дрейф мобов) с seed для воспроизводимости;
  - команды CLI/HTTP-триггеры (`GET /scenario/death`, `POST /chat`) для ручных тестов;
  - флаг `--chaos`: случайные обрывы WS (для тестов reconnect-политики).
- Используется в e2e-тестах CI.

## 6. Архитектура клиента

### 6.1 Технологический стек

| Слой | Выбор |
|---|---|
| UI | **eframe + egui** (последняя стабильная, зафиксировать в lock), `egui_extras` (таблицы/изображения), `egui-toast` |
| Асинхрон/сеть | `tokio` (rt), `tokio-tungstenite`, `futures-util` |
| Сериализация | `serde`, `serde_json` |
| Ошибки | `thiserror` (типы), `anyhow` (только bin-граница) |
| Логирование | `tracing` + `tracing-subscriber` + `tracing-appender` (rolling files) |
| Время | `time` (или `chrono`) — UTC epoch как канон |
| Конфиг | `toml` + `directories` (путь данных платформы) |
| Секреты | `keyring` (macOS Keychain / Windows Credential Manager / Secret Service) |

### 6.2 Процессы, потоки, модель данных

```
[eframe main thread]                [tokio runtime (1..2 worker threads)]
  app.update(dt):                    transport task:
   ├─ consume rx (mpsc<IngressEvent>)   ws read loop → decode → IngressEvent::Server
   ├─ AppStore::apply(event)            ws write loop ← Outbound::{Cmd,Close}
   ├─ UI = функция от AppStore          reconnect supervisor
   └─ действия UI → Outbound::Cmd       timers (access-token refresh, time.sync)
```

- **Единый AppStore** (struct state, не «бог»): `session, config, chars, snapshot{location,char,party,guild}, inventory_index, crime, quests, chat[per-channel ring], trade, ui_state, log` — всё производное только из событий.
- Редуктор `apply(IngressEvent) -> StorePatch` — чистые функции, доменные модули `reducer/*.rs`; **вся игровая логика представления (маппинг ошибок, capability-развязки, отсчёты) тестируется без egui**.
- egui: immediate mode; реактивные repaint — `request_repaint` по событиям/таймерам 1 Гц (для отсчётов); `run_while_visible` + низкая idle-частота, NFR §8.
- Смена персонажа = полный сброс доменов (кроме account/config).

### 6.3 Transport-слой (требования надёжности)

- Экспоненциальный backoff reconnect: 0.5s,1s,2s… до 30s, ±20% jitter; макс. попыток — безлимит, но после 10 — «ручное переподключение» подсказка.
- При восстановлении: `auth.resume` → (если ок) `state.resync` → UI «миг» из stale-стора, затем снапшот; индикатор статуса в заголовке: `online / reconnecting(3) / offline / auth_expired`.
- Команды: очередь исходящих с `seq`, таймаут ack 10 с, идемпотентный повтор ≤ 1 раза при «зависшем ack после reconnect» (только команды с `idempotent=true` в справочнике §4.7; бой/лут не повторяем).
- Все WS-ошибки/декоды пишутся в `tracing` с `seq/state_version`.

### 6.4 Локальное хранилище

- Каталог данных (directories): `config.toml`, `ui_state.json`, `logs/`, `cache/` (посещённые локации — LRU, без игровых ценностей!).
- Токены — только keyring, service `ld2.client`, account по хосту+логину.
- Никакого игрового состояния в persist (истина — сервер).

### 6.5 i18n

- Строки UI — в одном модуле `l10n` (ключ → ru/en), шрифты с кириллицей (dejavu/pt-sans из `egui` fontset — не «по умолчанию только latin»). Игровые тексты (бойлог, описания локаций) приходят с сервера — не локализуем.

## 8. Нефункциональные требования (НФР)

| Категория | Требование |
|---|---|
| Производительность | холодный старт ≤ 2 c (SSD); RSS ≤ 250 МБ при типовой сессии; UI-фризы ≤ 16 мс на событие (все тяжёлые редукции вне потока отрисовки); repaint ≤ 60 fps, idle ≤ 5 fps |
| Сеть | обработка 200 событий/с burst (stress-тест моком) без потери порядка; RTT-индикатор |
| Надёжность | reconnect без потери ack-семантики; ни один неизвестный тип/пол не должен ронять клиент (fuzz/табличные тесты); краш → автолог с seq/state_version предпоследних действий |
| Потребление ресурсов | история чата кольцевая (лимит настраивается), лог локации ≤ 10 000 строк, инвентарный индекс — O(1) по uid |
| Безопасность | wss-only в release; токены в keyring; запрет `ws://` в релизе (только dev build); телеметрия — локальные логи, без отправки на стороне клиента |
| Локализация | ru обязателен (P0), en — P1; шрифты с кириллицей; даты/числа — platform-locale |
| Доступность | все действия доступны клавиатурой; min font scale 12; контраст палитры AA |
| Совместимость ОС | Win 10+, macOS 12+, Linux (glibc 2.31+, X11 и Wayland — через winit/glutin; протестировать оба) |
| Обновления | semver приложения; проверка при старте (GitHub Releases API) — загрузчик не блокирует игру, «скачать» ведёт в браузер; force-min-version capability сервера (`protocol_features.min_client`) |

## 11. Тестирование

- **Unit**: редукторы (golden-состояния через insta), time_sync, capability-маппинг, chat-команды, ring-буферы.
- **Protocol**: serde round-trip + golden JSON (каталог `tests/golden/`), fuzz-подобный прогон «неизвестные типы/поля/versions» — клиент игнорирует и не падает.
- **Integration**: transport ↔ мок (reconnect, ack-timeout, resync, идемпотентность) — tokio::test.
- **E2E**: headless прогон сценариев мока + assertions на итоговое AppStore (UI-рендер вне автоматических проверок, кроме golden-снимков UI по желанию); отдельный e2e-матрикс: 2 клиента = social-сценарии.
- **Регресс производительности**: criterion-бенчмарк редуктора snapshot + стресс 200 событий/с (порог: p99 apply < 2 мс).
- Покрытие: reducer/transport ≥ 80% line, домены `crime/magic/upgrade` — с покрытиями формул §4.10.

## 12. Сборка, CI/CD, релизы

- **CI (GitHub Actions)**: матрица `[windows-latest, macos-15, ubuntu-22.04]`: fmt→clippy→test→build(debug) + e2e c моком.
- **Release (тег `vX.Y.Z`)**: артефакты:
  - Windows: portable `.exe` (+ `.msi` через `cargo-wix`, P1)
  - macOS: universal (arm64+x86_64) `.app` в `.dmg` (codesign+notarize — секреты CI, P1; без нотаризации — dev-only build)
  - Linux: `.AppImage` + `.deb`
- **Autoupdate**: проверка GitHub Releases при старте (не блокирующая), бейдж «есть обновление» + ссылка. Принудительная минимальная версия — capability сервера `min_client`.
- Версионирование семантическое; CHANGELOG по conventional commits.

## 13. Риски и меры

| Риск | Мера |
|---|---|
| egui неудобны для длинных логов (chat 5k) | кольцевые буферы + виртуализация (`egui_extras::TableBuilder`/свой clip-range), лимиты §8, бенч в CI |
| Контракт «живой» без сервера | всё через `ld2-protocol` crate + capability-флаги; несовместимые правки = bump `v` + CI-golden; мок держит «исторические» версии |
| Расхождение времени статусов на клиенте | серверные absolute-дедлайны + time_sync + полный re-apply снапшота после reconnect; локальный fallback-пересчёт |
| Раздувание UI-логики в render-функциях | редукторы чистые, UI = проекция стора (архитектурное правило CR) |
| Гонки событий (ack vs push) | `state_version` + правило «события монотонны по версии, старый ack игнорируется» |
| Кроссплатформенные шрифты/кириллица | фиксированный embedded font set (PT Sans/DejaVu) в assets, не системные |
| Wayland-специфика | ранний smoke-тест CI на Ubuntu Wayland/X11 (winit) |

## 15. Как работать по этому ТЗ (промпт-инструкция)

Агент-разработчик, исполняющий этот документ:

1. **Репо инициализировать ровно по §9**; не менять структуру без изменения ТЗ (правки ТЗ — отдельным PR с пометкой `[tz-amend]` и причиной).
2. **Итерировать по milestone M0→M9** (таблица §10) последовательно. Каждая задача = PR: conventional-commits (`feat: …`, `refactor: …`), link на ФР-xx/NFR-xx/§-раздел в описании PR.
3. **Не выдумывать контракт**: любое сообщение = типы из `ld2-protocol`; при нехватке — сначала amend §4 в этом документе, потом код.
4. **Capability-first**: любые лимиты/фичи из `evt/session.start` (§4.6); в коде запрещены хардкоды `MAX_CHARS` и подобных.
5. **Порядок внутри milestone**: `protocol → reducer/store → mock-сценарий → UI → тесты`; UI-фича без reducer-теста не мёржится.
6. CI-gate: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test --workspace` (включая e2e с моком).
7. Если требование неоднозначно: зафиксировать решение в §14-подобном «journal решений» репо (`docs/decisions/NNN-*.md`, ADR-формат, 1 страница) и продолжить — без блокировки.
8. **Definition of Done для всего продукта**: §10 (все milestone) + чек-лист §8 + руководство пользователя `docs/user-manual.md` + релизные артефакты трёх ОС, собранные в CI по §12.
