# ADR-013: Discovery подключения (домен → /.well-known/ld2.json)

**Дата:** 2026-11-16 · **Статус:** принято (все4 решения подтверждены
заказчиком) · **Связано:** `docs/protocol.md` §15 (вне WS-контракта),
`crates/ld2-server/src/app.rs` (маршрут рядом с `/healthz`),
`crates/ld2-server/src/config.rs` (`[discovery] address` — опциональная
секция), `plans/PLAN-M19.md` (фазы F19a–F19d), ROADMAP M19; TZ §12
(Autoupdate: `min_client`), TZ §8 (guard: внешний `ws://` запрещён)

## Контекст

Клиент хранит в конфиге **полный WS-URL** (`config.host`,
`ws(s)://…/ws`) и подключается напрямую. Перенос сервера на другой
адрес (миграция хостинга, прокси, смена порта) требует **перевыпуска
клиента**: старые сборки хранят мёртвый адрес. Принудительное обновление
старых клиентов (`min_client`) существует только внутри WS-сессии
(`evt/session.start` §5) — до подключения клиент не знает ни адреса,
ни требований.

Нужен уровень абове WS: клиент хранит **домен**, адрес и требования
берёт из стандартного well-known-документа; смена адреса сервера — без
правки клиентов; блокировка старых клиентов — до открытия сокета.

## Решения

1. **Формат документа** — `GET https://<домен>/.well-known/ld2.json`:

   ```jsonc
   { "address": "wss://game.example.com/ws",  // обязателен: WS-эндпоинт
     "version": 1,                            // версия WS-контракта (§2)
     "min_client": "0.18.0" }                 // опц.: из [server].min_client (§5)
   ```

   Документ — **вне WS-контракта** (не `[tz-amend]`, golden не меняется);
   спецификация — protocol.md §15.

2. **Два режима ввода** (обратная совместимость): ввод с `ws://`/`wss://` —
   прежний прямой путь (dev-мок, отладка; guard `host_allowed` — как
   раньше); любой другой ввод — **домен** → discovery: `https://<домен>/…`,
   в dev-сборке для localhost допустим `http://`.

3. **Валидация на клиенте** (до подключения): `address` — `ws(s)://` и
   guard release (§8); `version` ≠ версии клиента → отказ «контракт
   требует обновления клиента»; `min_client` > версии клиента → отказ
   «нужно обновление клиента» (сравнение — **строгое semver `>=`** —
   подтверждено заказчиком); недоступен/некорректен документ → ошибка
   без подключения. **Кэш** — до смены домена/рестарта; ошибки не
   кэшируются (ретрай при следующем подключении).

4. **Сервер**: опциональная секция `[discovery] address` (валидация:
   `ws://`/`wss://`; пусто/нет секции → маршрут `404` — discovery
   выключен осознанно); `min_client` берётся из существующего
   `[server].min_client` (§5) — дубля конфига нет. **Dev**: localhost
   отдаёт документ по http (подтверждено) — клиент в dev-сборке ходит
   `http://127.0.0.1:…/.well-known/ld2.json`.

5. **Keyring-ключ — домен** (подтверждено): адрес может меняться,
   логины/токены привязаны к домену и переживают смену `address`.

## Следствия

- `[discovery]` в `deploy/server.toml`/`server.example.toml` включён для
  dev (`ws://127.0.0.1:24817/ws`); прод-развёртывание обязано задать
  внешний `wss://`-адрес (за прокси) — иначе404 и клиенты на домене не
  подключатся (понятная ошибка).
- Тесты: `tests/discovery.rs` (200 + поля / 404 выключенного);
  резолвер клиента (F19b) — юниты на мок-ответах/границах semver.
- Мок сервера и `healthz` не меняются; маршрут не требует БД.
