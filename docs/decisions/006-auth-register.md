# ADR-006: Открытая регистрация `cmd/auth.register`

**Дата:** 2026-11-05 · **Статус:** принято · **Связано:** `docs/protocol.md` §4, §7, §9, §13;
`docs/tz.md` ФР-01; `plans/PLAN-M12.md` (D28), фаза M12.2

## Контекст

В контракте v1 есть только `auth.login`/`auth.resume` — регистрации нет: учётные записи
создавались бы вне протокола (SQL/CLI). Реальному серверу (M12.2) нужен штатный способ
регистрации игроков; заказчик выбрал добавление команды в протокол (вариант «CLI-инструмент»
отклонён).

## Решение

1. **D28 — новая команда `cmd/auth.register {login, password}`** (wire `v = 1` не меняется:
   §11.2 — новые `cmd/*` и `error.code` совместимы без bump). Ack — как у `login`
   (`{access_token, expires_in_s}`) + сразу `evt/session.start`: **регистрация = немедленный
   вход** (клиенту не нужен лишний round-trip).
2. **Лимиты — настройки сервера** (`[auth] min_login_len` / `min_password_len` в `server.toml`,
   D25): контракт фиксирует только коды ошибок, не числа. Мок использует константы 3/8 —
   дефолты шаблона конфига.
3. **Новые коды ошибок §9** (аддитивно, старые клиенты показывают `message`):
   - `E_LOGIN_TAKEN` — логин занят (фиксированные или уже зарегистрированные аккаунты);
   - `E_WEAK_PASSWORD` — логин/пароль короче лимитов (проверяется до уникальности);
   - `E_REGISTER_DISABLED` — флаг `auth.register_enabled = false` (закрытая регистрация
     для приватных серверов).
4. **Защита от спама/брута:** rate-limit по IP на `auth.*` → существующий `E_RATE_LIMITED`
   + `retry_after_s`; пароли — argon2id (D30), в логи/БД в открытом виде не попадают.
5. **Эталон поведения — мок** (`cmd/auth.register` реализуется в M12.2 одновременно с
   сервером); контрактные тесты — на обоих.

## Последствия

- Клиентские UI-экраны регистрации — **вне M12** (отдельный мини-milestone): команду
  поддерживают мок и сервер, текущие клиенты её не шлют и не ломаются (§11.5).
- Регистрация по TLS/WSS, как и логин (§4); `login`/`password` — только в payload команды,
  никогда в логах (D30).
- Новые аккаунты стартуют **без персонажей** (`characters: []` в `session.start`) —
  `char.create` дальше по контракту.
- Идемпотентность `+` (§7): ретрай после обрыва возвращает кэшированный ack и не создаёт
  второй аккаунт; повтор с новым `seq` → `E_LOGIN_TAKEN`.
