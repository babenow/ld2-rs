# ADR-007: Обязательный email при регистрации (D33)

**Дата:** 2026-11-06 · **Статус:** принято · **Связано:** `docs/protocol.md` §4, §7, §9, §13;
`docs/tz.md` ФР-01; `plans/PLAN-M13.md` (D33–D36), фаза M13.1;
ADR-006 (команда `cmd/auth.register`)

## Контекст

ADR-006 добавил в протокол `cmd/auth.register {login, password}` — регистрацию без
email. Заказчик уточнил модель M13: **основной идентификатор — логин, но email
обязателен и хранится на сервере** (без подтверждения кодом в v1 — задел под
восстановление пароля и служебную связь). Посылателей `email` ещё нет (клиентский
UI появляется только в M13), поэтому расширение payload **не ломает никого**:
старые вызовы без `email` отсутствуют.

## Решение

1. **D33 — wire-payload `cmd/auth.register` расширяется до
   `{ login, password, email }`** (wire `v = 1` не меняется — §11.2: новые
   обязательные поля в `cmd/*` допустимы, отправителей старой формы нет).
   `email` в `evt/session.start`/сводках персонажей **не входит** (вне M13).

2. **Нормализация — на сервере (источник истины):**
   `email = email.trim().to_lowercase()` перед вставью и сравнением; UNIQUE
   действует по нормализованному значению.

3. **Валидация синтаксиса (сервер, D33):** непустой после нормализации,
   ровно один `@`, домен содержит точку, длина ≤ 254, без пробелов/управляющих
   символов → иначе **`E_BAD_EMAIL`** (новый аддитивный код §9).

4. **Уникальность:** `accounts.email TEXT NOT NULL DEFAULT ''` +
   частичный `UNIQUE INDEX … WHERE email <> ''` (старые dev-строки переживают
   миграцию с пустым email; уникальность нужна только заполненным). Дубль →
   **`E_EMAIL_TAKEN`** (новый аддитивный код §9).

5. **Логин остаётся первичным идентификатором:** email нигде не используется
   для входа, `auth.login` по-прежнему `{login, password}`.

6. **Клиентская валидация минимальна (D34):** на экране регистрации ещё нет
   `evt/session.start` (лимиты §5) — клиент проверяет только непустоту полей,
   совпадение паролей и грубый синтаксис email; точные лимиты приходят
   кодами сервера (`E_BAD_EMAIL`, `E_EMAIL_TAKEN`, `E_WEAK_PASSWORD`,
   `E_LOGIN_TAKEN`, `E_REGISTER_DISABLED`, `E_RATE_LIMITED`) и показываются
   как есть (§9 fallback `message`).

7. **Пароль/email не попадают в логи и store-историю** (дух D30): поля живут
   только в стейте диалога регистрации.

## Последствия

- Контракт §4/§7/§9/§13 дополнен; golden-тесты `ld2-protocol` обновлены
  **до** клиентских изменений (§11.6); миграция БД — `0012_accounts_email`.
- Восстановление/смена пароля по email, подтверждение кодом — **вне v1**
  (задел в данных готов), анти-спам/captcha — вне объёма M13.
- Расширение payload обратно-несовместимо для *старых отправителей*
  регистрационных форм — риск нулевой (отправителей нет до M13).
