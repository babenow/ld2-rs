# ADR-012: Руна-слоты, ресурс рун и авто-приёмы при ударе

**Дата:** 2026-11-15 · **Статус:** принято · **Связано:**
`docs/protocol.md` §6 (Socket/снапшот), `content/items.json`,
`crates/ld2-server/src/config.rs` (`[gameplay.magic]` — режим и
интервал зарядов, `rune_recharge_s`; `[gameplay.resource]` — образец
`energy_regen_s`), `plans/PLAN-M14.md` (F58), миграция
`0026_item_rune_sockets`; ADR-002 (сокеты),
ADR-010 (бонусы предметов)

## Контекст

Сокеты сегодня описаны как `Socket { index, rune }` — **типа слота в
данных нет**, а правило «куда что вставлять» зашито дважды и по типу
предмета:

- клиент `inscribe_target_allowed`: `gem → только armor`,
  `rune → weapon|staff`;
- сервер `socket.insert` повторяет то же.

Отсюда: самоцвет в оружие невозможен, отличить руна-слот от слота
под самоцвет можно только по типу предмета. Плюс в UI все слоты
рисуются одинаково (`◈` заполненный, `○` пустой) и вперемешку в одном
списке.

**Заряды рун** (`RuneInfo.charges`) тратятся при касте, но
**не восстанавливаются вообще** — возвращаются только при извлечении
руны (`socket.extract`, отклонение M12.5b). Ключ конфига
`magic.rune_recharge` объявлен и валидируется, но **нигде не
применяется** — мёртвый. Для «особого приёма», который срабатывает
часто, этого мало.

**Ресурсы класса** (энергия/ярость) уже имеют образец: тикер в
`systems.rs` по `resource.energy_regen_s` — заряды рун восстанавливаем
по той же схеме.

Заказчик (M18/F58, ответы 2026-11-15): отдельный **руна-слот** со
**своим значком** (не `○`, не `◇`), в описании — отдельной второй
строкой и **первым**; слоты самоцветов — туда же; разрешить
**самоцветы в оружии**; у «Меча тысячи истин» и «Топора Драккара»
добавить руна-слоты; руна даёт **и урон, и бафф сразу**, срабатывает
**с шансом при ударе оружием** (без кнопки в хотбаре), перезарядка —
против спама, в параметрах руны — **затрата на применение** и
**лимит суммирования баффа**.

## Решение

### 1. Тип слота — в самом слоте (`Socket.accepts`)

Поле `accepts: rune | gem` в `Socket` (аддитивно, §11 — старый сервер
поля не шлёт, клиент фолбэчит по типу предмета):

```jsonc
{ "index": 0, "accepts": "rune", "rune": null }        // свободный руна-слот
{ "index": 1, "accepts": "gem",  "rune": { … } }        // слот под самоцвет
```

Именно поле в слоте, а не только число в `item_def`: клиенту нужно
видеть тип **каждого** слота (и для пустого), иначе нельзя отличить
руна-слот от слота под самоцвет в снапшоте.

Сервер проставляет `accepts` при отправке снапшота (выходные данные
считаются из `item_defs.rune_sockets` предмета).

### 2. Число руна-слотов — отдельное поле определения

**Уточнение заказчика (F58):** руна-слоты — не в `stats`, а отдельным
полем определения, как обычный `sockets`. В `content/items.json` —
верхнеуровневое поле `rune_sockets: N`; в БД — колонка
`item_defs.rune_sockets` (**миграция 0026**, `NULL` = не указано).

`NULL`/отсутствие → дефолт по типу предмета:

- броня — 0 (все слоты под самоцветы);
- посох — `N = sockets` (все рунные, самоцветы в посох по-прежнему не
  идут);
- оружие — по контенту (без поля — как посох, все слоты рунные).

Указанное значение `N`: первые `N` слотов индексов →
`accepts: "rune"` (**руна-слот первым** — совпадает с требованием UI),
остальные → `accepts: "gem"`. Тип предмета перестаёт решать, куда что
вставлять — это решает `accepts`.

*Отменяет* прежнее решение «`stats.rune_sockets` без миграции» — поле
в статах заменено колонкой (семантика не меняется, только форма).

### 3. Инкрустация: руна по `accepts`, самоцвет — в оружие разрешён

Правило в одну сторону: сервер при `socket.insert` сверяет
`принимает ли слот` (его `accepts`) с типом вставки. Клиентский
`inscribe_target_allowed` (фильтр списка кандидатов) переписывается под
то же правило: руна → предмет с есть свободным `accepts=rune` слотом,
самоцвет → свободный `accepts=gem` слот (отсюда гемы в оружие).

### 4. Ресурс рун: те же `charges`, восстановление тикером

`charges/max` остаются (уже в `RuneInfo` и в raw-JSON сокета) —
это ресурс. Меняется только его получение: тикер в `tick.rs` (секундная
ветка, как `regen_step`) по аналогии с `resource.energy_regen_s`
возвращает заряды со временем — секунды **из конфига**.

**Решение по ключу (F58c, принято реализацией):** `magic.rune_recharge`
перестаёт быть декоративным — это режим:
- `time` — тикер: аккумулятор в тик-лупе, каждые `rune_recharge_s`
  секунд онлайн-персонажам +заряд (до `max`); изменения — CAS-записью
  (не затираем параллельный каст) + патч `evt/item/state` владельцу;
- `item` — прежнее поведение (заряды только при извлечении).

Валидация: режим ∈ {`time`, `item`}, `rune_recharge_s > 0`.
Значение уходит клиенту в `features.magic.rune_recharge` (§5) без
изменения контракта.

Расход: **не при каждом применении**, а при **срабатывании приёма**
(см. §5) — заряды защищают от спама. Затрата — поле руны `cost`
(деф. 1, кламп ≥ 1; читается в `systems::rune_charge_cost`):
применяется и при касте руны (сейчас −1 заряд, теперь −`cost`), и при
авто-приёме (§5/F58d) — одна точка чтения.

### 5. Авто-приём: срабатывает при ударе, без кнопки

Кнопки в хотбар нет: при ударе оружием (`plan_combat` в `tick.rs`)
шанс руны решает, сработает ли эффект. Руна задаёт **и урон, и бафф
одновременно** (оба поля в её параметрах):

- **урон** — по формуле как у `rune_cast`, но без требований маны;
- **бафф** — временный эффект персонажа со стаками.

Затрата — поле руны (`cost`, по умолчанию 1), снимается при
срабатывании; нет зарядов → не срабатывает.

**Кэш в `world`** обязателен: `plan_combat` не ходит в БД, а сокеты
хранятся в БД. Руны персонажа кэшируются в `world` по образцу
`char_hits`/`char_attack` (обновление на входе в мир, экипировке,
инкрустации).

### 6. Баффы: стаки + тикер (новая подсистема)

Подсистемы баффов в проекте нет; ближайший образец — таймеры
статусов преступности (tick-паттерн) и `CharacterState.crime`.
Добавляется `CharacterState.buffs` (стак + `expires_at`) для
отображения в окне персонажа. Лимит суммирования — `max_stacks` из
параметров руны; бафф сверх лимита не накладывается.

### 7. UI: значок и строки

- **новый значок руна-слота** (не `○` пустой, не `◇` как сейчас у
  заполненного) — отличим на глаз. **Решение (F58):** знаки рун рисуются
  **шрифтом Dwarven Runes** (`assets/fonts/dwarven-runes.ttf`, embedded;
  глифы `a–z`, семейство `"Dwarven Runes"`); ключ глифа — имя руны
  (djb2 → стабильный `a..=z`), пустой руна-слот — фиксированный глиф;
  хелпер — `ld2_client::rune_glyph` (одна точка правды); слоты
  самоцветов остаются на прежних `◈`/`○`;
- **глиф настраивается в самой руне**: контент-поле `stats.glyph` (одна
  латинская буква — валидация контента) → wire `RuneInfo.glyph`
  (`[tz-amend]`, аддитивно §11) → при вставке копируется в сокет;
  клиент берёт поле, без него — фолбэк хешем имени (старые
  руны/серверы);
- в описании слоты переезжают на **вторую строку** под заголовком
  «редкость · тип · +N», руна-слот **первым**, слоты самоцветов после;
- делегаты списков-окон: одинаковая высота, текст по вертикальному
  центру.

## Следствия

- Wire-контракт меняется (`Socket.accepts`, `CharacterState.buffs`) —
  только через `[tz-amend]` + эта запись + golden-тесты.
- Старые снапшоты без `accepts` продолжают работать (фолбэк по типу
  предмета — прежнее поведение).
- `content/items.json` — у существующих предметов `rune_sockets` не
  указан (`NULL`) → дефолт по типу → поведение как сегодня (кроме
  оружия, где разрешены гемы: слоты под самоцвет станут доступны для
  оружия); у «Меча тысячи истин» и «Топора Драккара» —
  `rune_sockets: 2` отдельным полем.
- Число руна-слотов у «Меча тысячи истин» и «Топора Драккара» —
  **2 из 4** (половина под руны, половина под самоцветы): решение
  принято реализацией, обратимо одной строкой в контенте.
